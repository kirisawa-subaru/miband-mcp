# Gadgetbridge 到电脑实测（2026-09-21）

## 结论与范围

已跑通国内版小米运动健康提取既有配对密钥、Gadgetbridge 连接手环、同步活动、导出数据库及通过 USB ADB 传到电脑。第二次执行同一数据流程，电脑库的活动记录由 60 条增至 94 条，最新观测时间推进；证明取到新记录，而非只复制了一份旧文件。

初次安装验证到电脑文件传输为止。随后已实现并验通 Gadgetbridge MCP 后端，见 [MCP 配置与验收](gadgetbridge-mcp.md)；选择后端需显式配置，旧小米健康缓存不会自动变成 Gadgetbridge 数据源。

测试使用已有开发环境与设备记录，不能视为全新、无预先授权手机的安装验收。手机本身是已有 root 的测试机；后续应在不带个人设备技能及授权的独立环境，另测普通用户从首次插线开始的流程。

## 环境与证据

- 安卓 14、一加 Ace3、小米手环 10。
- 国内版小米运动健康 3.59.1；Gadgetbridge 0.94.0。
- 电脑：Linux；最终文件传输为指定目标设备的 USB `adb pull`。
- 手机与电脑导出文件均为 884,736 bytes，两端 SHA-256 一致。
- 电脑库 `PRAGMA quick_check` 为 `ok`，Gadgetbridge schema version 为 140。
- 初次库含一台设备、60 条带心率的活动记录、日汇总及电量记录；重复同步后的活动记录为 94 条。睡眠与手动测量表为空，未以缺失补零。
- 重复流程分别观察到活动同步完成、数据库导出成功事件，再拉取并核对文件。发送 Intent 成功不单独作为完成证据。

公开记录不包含密钥、原始日志、设备唯一标识或个人健康数值。实际数据库、截图及配置均保存在用户本地私有运行目录，不纳入 Git。

## 实际遇到的问题与安装流程修订

| 现场问题 | 修订后的流程 |
|---|---|
| 用户看到充电，但没有数据连接提示 | 说明支持数据传输的线，可用包装盒原装线；解释如何下拉通知栏，允许用户用截图描述现状 |
| “关于”页反复点击 Logo，没有出现预期迁移提示 | 先检查已有日志能否读取；确认控件后仍无响应时换入口，不重复盲点 |
| 设备日志中的 `huamiAuthKey` 为空 | 综合实际存在的主日志、设备日志与轮转文件；本次候选在主日志的其他字段中 |
| 用户担心“连接新手机”会更换密钥 | 说明继续复用既有密钥，区别于官方 App 解绑/恢复出厂；提前说明二维码无需扫描 |
| Gadgetbridge 请求大量权限，并跳到安卓设置页 | 解释权限归属与用途，区分必要/可选，询问代点或手动；区分发布通知与读取通知 |
| Android 留有旧蓝牙绑定 | 根据实际配对提示处理系统蓝牙 bond，区别于官方账号解绑；本轮移除旧 bond 后正常配对 |
| 配对需要手机与手环双端确认 | 提前一起说明，两端由用户手动确认；agent 继续只读观察，已连接后不再索要口头确认 |
| 自动导出关闭时，导出位置不可配置 | 先启用自动导出，再进入保存位置选择；用户选好后由 agent 截图读取并验证，不让用户抄路径 |
| 操作 agent 停在检查点，安装监督等待人工确认 | 明确人工输入与只读观察的边界；普通 App 操作不因用户选择手动处理系统权限而全部暂停 |

## 可重复的数据路径

1. 保持 Gadgetbridge 与手环连接；手机通过 USB 连接已授权电脑。
2. 通过 Gadgetbridge 已启用的活动同步 Intent 请求记录同步，观察本次完成事件。
3. 触发数据库导出，观察本次成功事件；失败时保留电脑已有可读副本。
4. 从设置中确认的实际共享存储位置拉取数据库，核对两端哈希及 SQLite 完整性，再读取。
5. 分别检查导出时间、复制时间和记录自身的观测时间；需要新记录时核对最后一项是否推进。

本轮在 Gadgetbridge 中开启了活动同步触发/完成广播、数据库导出触发/完成广播，蓝牙 Intent 控制开关保持关闭。自动导出保留应用默认的每三小时周期，另外已验通按需触发；未声称手机熄屏长期稳定、无线或跨网络传输已经通过。

## 后续 MCP 接入实测

同日已将同步、导出、校验与原子替换封装为 MCP 的 `sync_health`。真实 stdio 客户端调用后，最新观测从 03:52 推进到 03:53 CST；最近状态、日报和明细均读取 Gadgetbridge 数据，模拟目标手机不可用时旧缓存仍可查询。本阶段只使用 USB ADB 和 Gadgetbridge 已授权的 Intent，没有调用 root/SSH/Frida。

曾出现手机已发出完成事件、电脑端仍等待至超时的故障。修复后的完整 MCP 调用通过；这也说明独立手机命令成功不能替代实际 MCP 客户端验收。
